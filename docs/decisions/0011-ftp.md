# 0011 — FTP and FTPS downloads

- Status: accepted
- Date: 2026-11-14

## Context
Users still meet `ftp://` links (mirrors, firmware, university archives, NAS boxes) and
expect a download manager to handle them with the same pause/resume and speed limits as
HTTP. The engine now has a protocol plug-in point (`engine.Protocol`, commit 02d26f6), so FTP
only has to move bytes into `Job.PartPath`. We had to pick a client implementation, a TLS
policy, a resume strategy and a test server.

## Decision
- **Own small client** in `engine/proto/ftp` (kind `"ftp"`), standard library only
  (`net`, `net/textproto`, `crypto/tls`). It needs a handful of commands: `AUTH TLS`,
  `USER`/`PASS`, `PBSZ`/`PROT P`, `TYPE I`, `SIZE`, `EPSV`/`PASV`, `REST`, `RETR`, `QUIT`.
  Owning the sockets lets us close every connection when the context is cancelled (prompt
  pause), put deadlines on every control reply and data read, and tell "server does not
  offer TLS" apart from "TLS handshake failed".
- **TLS:** `ftps://` is implicit TLS (port 990). On `ftp://` we send `AUTH TLS` and upgrade
  when the server accepts it; if it is refused we continue in plain FTP, as the address
  asked. If the server accepts `AUTH TLS` but the handshake fails (e.g. untrusted
  certificate), a download with a password stops with a clear error and the password is never
  sent; an anonymous download reconnects in plain FTP (nothing secret is at stake).
  Certificates are verified against the system roots (TLS 1.2+); a TLS session cache lets
  the data channel resume the control channel's session, which many servers require.
  `WithTLSConfig` exists for tests and future "trust this server" settings.
- **Credentials** from the URL userinfo, else `anonymous`/`anonymous@`. Errors never contain
  the URL: `url.Parse` errors are not wrapped, server replies have the password scrubbed, and
  the engine's `redact` now also strips userinfo from `ftp://`/`ftps://` URLs.
- **Resume:** the part file's size on disk is the offset for `REST`; `SIZE` gives the total.
  The remote size is saved as resume state, and a different size on resume restarts from
  zero (the file changed). A server that refuses `REST` restarts from zero too.
- **Passive mode only** (EPSV, falling back to PASV). The data connection always goes to the
  control connection's IP; the address in a PASV reply is ignored (no FTP bounce to another
  host, works with servers behind NAT that announce private addresses).
- **One connection per download.** Many servers limit logins per user/IP (often 1–3 for
  anonymous) and refuse extra ones; segmenting with several logins needs per-server probing
  and fallback. Single-stream FTP is usually fast enough; this can be revisited.
- **Retries:** the engine does not retry protocol downloads, so the client retries transient
  failures itself (network errors, 4xx replies, early close): up to 5 attempts with
  exponential backoff from 1 s, reset whenever an attempt made progress. 5xx replies
  (bad login, missing file) and certificate failures are final.
- **Timeouts** follow the HTTP client: 30 s dial, 20 s TLS handshake, 60 s per control reply
  and 60 s without data on the data channel.
- **Tests** run against `github.com/fclairamb/ftpserverlib` (MIT) over an in-memory
  `afero` FS — an independent, widely used server implementation, so the client is not only
  tested against our own understanding of the protocol. They are test-only dependencies:
  they appear in `go.mod` but are not linked into any binary.

## Alternatives considered
- `github.com/jlaffaye/ftp` — mature and widely used, but: data connections are dialled
  without the context (a pause can wait for the 30 s dial timeout), control replies have no
  read deadline (a silent server hangs the download), a custom dial function disables TLS on
  data connections, and `AUTH TLS` failures and handshake failures are not distinguishable.
  Working around those would mean wrapping its sockets anyway, for a feature set we need
  only a tenth of.
- A minimal FTP server in `internal/testsrv` — less dependency weight, but then client and
  server would share the same assumptions; a real third-party server finds more bugs.
- Refusing plain FTP when a password is given and the server offers no TLS — safer, but
  breaks many LAN/NAS servers that only speak plain FTP, and `ftp://` already states the
  user's choice. The UI may warn about it later.
- Active mode (PORT/EPRT) — needs inbound connections through the user's firewall/NAT;
  passive works almost everywhere.

## Consequences
- FTP downloads get the engine's queue, pause/resume, part file, checksums, Mark-of-the-Web
  and speed limits for free; `Job.Received` is called for every chunk.
- No new runtime dependency; two test-only ones (`ftpserverlib`, `afero`).
- The engine's HTTP proxy setting does not apply to FTP: connections are direct.
- Passwords live in the download URL. They stay out of errors and logs, but the URL is stored
  in the database and returned to local clients (UI, extension host) like any other download
  URL. Stripping userinfo from snapshots, or keeping credentials elsewhere, is follow-up work.
- Directory URLs and recursive downloads are not supported (the URL must name a file).
